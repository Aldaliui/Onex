# مرحلة AR — ربط المبيعات بالمخزون

تضيف هذه المرحلة ربط فاتورة البيع بالمخزون والمحاسبة. عند ترحيل فاتورة AR، لا يتم تقييم تكلفة البضاعة بسعر البيع، بل باستخدام متوسط تكلفة المخزون الحالي في المستودع.

## Migration

```text
cloudflare/d1/0008_ar_inventory_posting.sql
```

تضيف:

- `cogsJournalNo` إلى `invoices`.
- `inventoryPostedAt` إلى `invoices`.
- `appliedUnitCost` إلى `invoice_lines`.
- `appliedCostTotal` إلى `invoice_lines`.
- فهارس الربط بين الفاتورة وحركة المخزون وقيد COGS.

## دورة البيع

يستمر إنشاء الفاتورة عبر:

```http
POST /api/erp/invoices
```

ويمكن إنشاء فاتورة في حالة `DRAFT` أو تمرير:

```json
{"postNow": true}
```

عند الترحيل:

```http
POST /api/erp/invoices/:id/post
```

ينفذ Worker الخطوات التالية داخل `D1 batch`:

1. التحقق من وجود الفاتورة وحالتها.
2. قراءة أسطر الفاتورة.
3. قراءة رصيد كل صنف في المستودع.
4. رفض العملية عند عدم كفاية المخزون.
5. حساب متوسط التكلفة الحالي لكل صنف.
6. تقييم الكمية الخارجة على متوسط التكلفة.
7. تحديث `stock_balances`.
8. تسجيل `SALE_ISSUE` في `stock_movements`.
9. حفظ التكلفة المطبقة في `invoice_lines`.
10. إنشاء قيد المبيعات.
11. إنشاء قيد COGS.
12. تحديث الفاتورة إلى `POSTED`.
13. حفظ `cogsJournalNo` ووقت خصم المخزون.
14. تسجيل حدث التدقيق.

## مثال

المخزون قبل البيع:

```text
الكمية: 10
متوسط التكلفة: 10
قيمة المخزون: 100
```

فاتورة البيع:

```text
الكمية: 3
سعر البيع: 20
إجمالي البيع: 60
```

النتيجة:

```text
تكلفة الوحدة المطبقة: 10
تكلفة المبيعات: 30
رصيد المخزون: 7
قيمة المخزون: 70
```

قيود GL:

```text
AR Sale:
مدين  1100 العملاء       60
دائن  4100 المبيعات       60

COGS:
مدين  5100 تكلفة المبيعات 30
دائن  1300 المخزون         30
```

## منع الترحيل المتكرر

إذا كانت الفاتورة `POSTED`، فإن إعادة استدعاء post تعيد نتيجة idempotent ولا تنشئ حركة أو قيداً جديداً:

```json
{
  "invoiceId": 1,
  "status": "POSTED",
  "idempotent": true
}
```

## فشل الرصيد

عند محاولة بيع كمية أكبر من المتوفر، ترجع العملية:

```json
{
  "error": "INSUFFICIENT_STOCK",
  "details": {
    "itemId": 1,
    "available": "7.000000",
    "required": "20.000000"
  }
}
```

وتبقى الفاتورة `DRAFT` ولا يتم إنشاء أي حركة أو قيد.

## ملاحظة التزامن

يستخدم تحديث الرصيد `versionNo` مع شرط الكمية والإصدار. يجب إضافة retry على مستوى العميل أو Worker عند ظهور تعارض متزامن، مثل:

```text
409 STOCK_BALANCE_CHANGED_RETRY
```

## اختبار المرحلة

تم التحقق محلياً من:

- استلام 10 وحدات بسعر تكلفة 10.
- بيع 3 وحدات بسعر بيع 20.
- حساب COGS بقيمة 30 وليس 60.
- تحديث الرصيد إلى 7 وقيمته إلى 70.
- إنشاء قيد COGS متوازن 30/30.
- إنشاء قيد المبيعات متوازن 60/60.
- رفض بيع 20 وحدة مع توفر 7 فقط.
- إبقاء الفاتورة المرفوضة في `DRAFT`.
- منع إعادة ترحيل الفاتورة المرحّلة.
- نجاح `PRAGMA foreign_key_check`.
